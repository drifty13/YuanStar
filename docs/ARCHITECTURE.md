# 架构说明

NiceGUI 让本地 Python 项目以很小的运行骨架提供可人工验收的网页界面。`app.py` 只装配页面和处理 UI 事件；`session.py` 管理内存会话、快照、撤回/重做、筛选和受控状态修改；`domain.py` 负责模型、严格整数解析、汇总键合并、共享排序和数量校验文案。页面不自行计算合并、排序或差值。

`NotImplementedVisionPipeline` 仍可作为显式无 OCR 占位；Phase 0.3 的 `LocalOfflineVisionPipeline` 仅在本机 NiceGUI 会话中桥接既有 `OfflineSingleImagePipeline`，并通过后台 I/O 任务避免阻塞页面。它只将完整且名称、等级、品质均可用的卡片交给 `SessionState`；图片池、用户确认的有向重叠关系和 OCR 原始坐标留在 vision/UI 边界，不进入业务汇总或 Excel。截图尺寸读取仍位于 `vision/image_metadata.py`，绝对像素坐标不进入业务模型、会话或 Excel。

`data/star_catalog.json` 与 `data/ocr_aliases.json` 是词典边界。词典顺序同时驱动网页与 Excel 的规范化排序；别名也用于搜索归一化。修改名称、别名或未来可选展示/用途字段不需要修改 OCR 或导出结构。

MVP0 使用内存状态与轻量快照栈，不使用 SQLite、ORM、仓储层、微服务或插件框架。MVP1 再引入 SQLite、多账号和历史快照；MVP2 再做养成计划。未来 MaaYuan 通过本地接口或共享文件松耦合，而不直接耦合代码。

## 阶段状态

Phase 0.2C 已关闭：259 条有效出现，经 12 对自动确认和 1 对人工确认的有向重叠后为 207 条唯一记录；明确碎片以 `exclude_fragment` 留痕且不进入清单。Phase 0.3 已将本机离线流程接入网页试运行；它不自动推断跨图重叠，用户必须先确认图片池并显式标记关系。

## 未来 OCR 的架构边界

真实识别优先接入预训练 OCR。私有截图用于回归、阈值和布局验证，不预先训练自定义深度学习模型；只有固定失败模式持续出现，才单独评估微调或专项分类器。支持原始星石背包的手机/平板竖屏 PNG/JPG/JPEG（可含黑边、分辨率差异、轻压缩和红点），不支持横屏、拍摄屏幕、严重上下裁切、拼图布局、极端模糊/滤镜/遮挡或不同游戏 UI。

vision 层未来按“解码和方向归一化 → 有效游戏视口/黑边裁切 → 稳定锚点 → 手机/平板布局 profile → 归一化坐标 → 完整卡片检测 → 局部 OCR → 词典/置信度 → 人工复核”组织。锚点是“星石背包”标题、页签、背包数量和固定四列；profile 只保存比例/归一化坐标，业务层不保存像素坐标。黑边/视口、模板或指纹锚点、几何变换、OCR 文本锚点、圆形/列/行几何、相对裁切、profile 与人工兜底仅是可替换的 vision 策略。
