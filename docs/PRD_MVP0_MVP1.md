# YuanStar 需求基线

## 已确认事实

- 本地工具同时支持《如鸢》《代号鸢》；当前星石规则共用，数据保留 `game_version`。
- 主星 14 种、辅星 24 种；两者计入背包数量。橙星曜、紫星曜、白星曜仅记录数量，不计入背包数量。
- 等级为 1–60，只记录当前等级，不推断突破。合法品质为橙、紫、蓝、绿、白。
- “双抗”不是正式星石名称；紫薇归一为紫微，紫星耀/白星耀归一为紫星曜/白星曜。
- 截图可无重叠或有重叠；未来不得仅按名称、等级、品质去重。完整性校验仅警告，不自动删除记录。

## 本轮实现（Phase 0.1 / MVP0 骨架）

- 内存会话、导入替换恢复点、最近 30 步撤回/重做。
- NiceGUI 导入页和人工核对页；Phase 0.3 已接入本机离线 OCR 试运行，识别前须确认，只有完整且字段可用的卡片才进入可编辑汇总。
- 手工维护主星/辅星汇总，按大类、名称、品质筛选；网页不显示独立品质列，非橙品质嵌入名称。
- 橙星曜、紫星曜与白星曜手工录入、背包数量校验、三工作表 Excel 导出。
- Phase 0.1.1：严格校验人工数字输入；同一“大类、标准名称、品质、等级”自动汇总；按词典顺序稳定排序；搜索支持别名和多名称 OR；背包信息可在人工核对页修改。

## 后续阶段

- MVP1：多账号、SQLite 持久化、历史快照、备份和跨重启恢复。
- MVP2：养成计划、升级经验、突破状态与材料计算；默认不确定且允许人工修改。
- Phase 0.2C 最终关闭使用视觉品质证据、截图重叠和人工复核生成候选唯一清单；重叠只由用户标记的同池有向关系触发，绝不将相同名称、等级、品质当作去重键。

### 后续阶段待办（仅记录，不在本轮实现）

- 正式计划背包编辑：以当前背包数据为初始基线，计划侧支持人工编辑；等级受 1–60 等约束，名称、大类、品质等共享字段的同步规则必须明确。当前背包与计划背包须能明确选中、进入各自的编辑区并使用可区分的高亮；计划编辑不得改写当前数据，实例 ID 仍须稳定，并补充历史、备份、重新识别后的 ID/关联审计。**固定排序契约：** 计划侧没有独立排序或分组；即使未来计划等级、品质、名称或其他计划字段改变，右侧仍必须按左侧当前背包的 `star_instance_id` 顺序、大小类分区、小组分组和组内顺序展示，计划字段只改变该行的右侧显示值，不得移动实例行。
- OCR 与人工分配扩展：补齐平板经验星曜识别、外部局部/指定区域 OCR，以及未分类图片的人工分配流程。它们须沿用既有图片池确认、导入失败不覆盖、重叠标记与 OCR 证据保留约束后，再单独设计和实现。

## 阶段状态

Phase 0.3 已完成本地网页试运行：多图上传、图片池确认、用户标记的有向重叠、显式识别确认、完整卡片写入、人工核对和 Excel 导出均可在本机会话完成。网页不公开部署，不生成 EXE，也不保存图片或使用 SQLite。经验页真实样本尚未覆盖，缺失时必须明确为未验证而非虚构 OCR 结果。

### 未来 OCR 原则

- 优先使用预训练 OCR；截图作为回归、阈值和布局数据，不在前期训练自定义深度学习模型。仅在持续、固定失败模式下评估微调或专项分类器。
- 支持原始星石背包截图、手机/平板竖屏、PNG/JPG/JPEG、不同分辨率和黑边、基本完整 UI、轻度压缩或红点；不支持横屏、拍摄屏幕、严重上下裁切、拼图软件布局、极端模糊/滤镜/遮挡及完全不同游戏 UI。
- 管线将依次完成解码/方向归一化、有效游戏视口/黑边裁切、稳定锚点、手机/平板布局 profile、归一化坐标、完整卡片检测、局部 OCR、词典/置信度和人工复核。锚点为“星石背包”标题、页签、背包数量、固定四列；布局 profile 用比例/归一化坐标，业务层没有绝对像素坐标。
- 黑边/视口、模板或指纹锚点、几何变换、OCR 文本锚点、圆形/列/行几何、相对裁切、profile 与人工兜底仅记录为候选策略。

### MVP2 仅记录的双栏养成计划

MVP2 计划采用左右双栏：左侧为当前/背包/原始数据，右侧为计划。计划可复制当前值作为初始值，但计划编辑不得修改当前数据；共享编辑器必须显式标明正在编辑哪一侧，并用不同高亮区分。两侧都可混合主星和辅星，计划数量可小于当前数量；下一次 OCR 不得静默覆盖计划。此处仅记录需求，不实现 UI、升级、突破或材料计算。
