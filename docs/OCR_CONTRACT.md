# 未来 OCR 契约

`VisionPipeline.analyze(images, batch) -> AnalysisResult` 接收任意顺序的图片与导入批次。Phase 0.3 的本机实现自动给出页面类型候选；用户在网页确认主星、辅星、经验或待确认图片池后，才能标记同池的有向重叠关系。输入须支持手机和平板、黑边、不同分辨率。

网页未来输出以逐颗 `DetectedStarItem` 为主：保留来源图片、相对位置、原始名称/等级/品质、最终人工值、置信度和完整卡片判断。离线 Phase 0.2C 使用独立的 `SingleImageAnalysis` / `RecognizedStar` 契约，保留原始和规范名称、直接 OCR 等级快照、最终等级、`level_source`、品质视觉证据、置信度、相对和原图坐标；还保留背包数量候选及跨图视觉重叠候选。

不得依据名称、等级、品质直接去重；去重必须依赖用户确认的有向截图重叠、行上下文、相对位置、头像或锁定图标等视觉证据。不完整截图可以输出批次结果，但半截或不可可靠读取卡片不应计入。低置信度和原始值必须保留给人工复核。视觉品质仅使用橙、紫、蓝、绿、白；不可靠时为 unknown，绝不默认橙。装备状态默认 `not_evaluated`，只允许人工或冲突驱动复核改变，不能对全量卡片做臆测分类。

等级 OCR 的直接快照与最终等级分离：`level_source` 为 `direct_ocr`、`sort_order_inference` 或 `manual`。排序推断只读取同图连续阅读顺序中的直接 OCR 快照，且仅在合法区间唯一时补全；它不参与下一颗推断，也不触发新的名称推断。

经验星石独立于普通品质：已确认种类为橙星曜、紫星曜、白星曜。三者都不计入背包普通星石数量；只有经验页分类可靠、页签选中、展示区域完整、没有裁切警告、所有可见图标已分类且顺序合理时，未出现种类才可记录为 0，否则必须为 unknown。

游戏 UI 更新时主要替换 `vision/` 模块和布局配置，而不改变账号、导出、筛选或未来养成模块。Phase 0.1 的空实现必须明确 `executed=False`。

## 未来识别原则与截图边界

真实 OCR 优先采用预训练 OCR；截图首先作为回归、阈值和布局数据，而不是预先训练模型的理由。只有出现持续、固定且可复现的失败模式时，才评估微调或专项分类器；MVP0 不引入自定义深度学习训练。

支持原始星石背包截图、手机或平板竖屏、PNG/JPG/JPEG、不同分辨率与黑边、基本完整的游戏 UI，以及轻度压缩或红点遮挡。不支持横屏、拍摄屏幕、严重裁掉顶部或底部、拼图软件布局、极端模糊/滤镜/遮挡，或完全不同的游戏 UI。

未来管线顺序为：解码和方向归一化 → 有效游戏视口/黑边裁切 → 稳定锚点定位 → 手机/平板布局 profile → 归一化坐标 → 完整卡片检测 → 局部 OCR → 词典与置信度 → 人工复核。稳定锚点包括“星石背包”标题、页签、背包数量和固定四列卡片；布局 profile 使用比例/归一化坐标，业务层不得出现绝对像素坐标。

可并行评估的策略只记录为未来设计：黑边/视口识别、模板或指纹锚点、几何变换、OCR 文本锚点、圆形/列/行几何、相对裁切、布局 profile 与人工兜底。它们不构成当前 OCR 实现或自动识别承诺。

## Phase 0.2B.1 修复约束

顶部裁切不等于首行星石不完整：当标题或标签缺失时，vision 层必须以近全视口的四列圆形网格降级搜索，并只根据图标、名称和等级区域判断完整性。页面词典 fallback 完成后必须重算每颗星石的复核状态。样本元数据通过 SHA-256 与实际路径对账；`scroll_position` 已弃用，OCR 和未来多图逻辑不得依赖它。
